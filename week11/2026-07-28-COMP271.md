## Revisiting the Hashing Hotel

We picked back up with yesterday's hotel metaphor: a guest is assigned a room based on the first letter of their last name, giving $\mathcal O(1)$ lookup at the cost of wasted rooms and collisions (Temeeka's "Glass" versus Alex's "Garcia," both starting with G). We reviewed the hash method itself — pull the first letter, uppercase it, subtract the ASCII value of 'A' — and confirmed in code that swapping subtraction for the modulo operator produces the same guarantee: no two letters ever land in the same room, since no value from 0 through 25 is a multiple of 26.

## Probing, Then Chaining

We first extended the hotel with probing — if your assigned room is taken, take the next open one — but saw it degrades quickly as more guests share a first letter. Building a four-room hotel live with student last-name initials, we let colliding guests hang off the room on a "hammock" instead, which we recognized as nothing more than a linked list attached to each array slot — an array of linked lists.

## Assembling the Hash Table

Generalizing: an array of 1,000 slots, each holding a linked list capped at 5 nodes, stores 5,000 objects total, findable in at most 6 steps (1 to locate the slot, 5 to walk the list) — this structure is the hash table (also called a hash map or hash set). We discussed the space-for-time trade-off behind it, and previewed tomorrow's topic: keeping no more than 75% of slots filled and resizing (doubling and rehashing) once that limit is reached, much like a box office splitting one ticket line into more as demand grows.
