## Generics: Decorative in Python, Substantive in Java

We wrapped up the `Node` discussion by contrasting how Python and Java handle "any type of data." In Python, the type annotations we wrote are purely decorative — we could describe the same intent in a comment and the code would behave identically. In Java, the equivalent notation is substantive: it's enforced by the compiler. We keep circling back to Java because COMP 272, the next course in the sequence, is taught in Java, so part of our design is to build familiarity with it alongside Python.

## Building the Doubly Linked List's `add` Method

Continuing the `DoubleLinkedList` class from yesterday, we wrote the `add` method. If the list is empty (`_head` is `None`), the new node becomes both head and tail. Otherwise, the new node is linked after the current tail and becomes the new tail. Either way, the node count is incremented — a concrete example of trading space for time: maintaining a running count costs a few bytes of memory but avoids re-traversing the whole list every time we need to know its size.

## Bidirectionality as a Design Choice

Using escalators, undo/redo (Control-Z/Control-Y), and one-way cassette tapes as analogies, we distinguished unidirectional from bidirectional linked lists. We revised the constructor to accept a `bidirectional` parameter (default `True`), so that setting a new node's `_previous` pointer only happens conditionally. Alexander asked whether a right-to-left unidirectional list would just swap head and tail — Leo agreed that's the simpler way to get that behavior, rather than modifying `add` itself. We closed by discussing that in real software design, understanding *why* a requirement is being asked for matters as much as writing the code.
