## Warm-up: a technical interview scenario

We opened with a discussion of technical interviews in industry — how companies like Google increasingly expect fluency with AI tools rather than memorized syntax, and how interviewers deliberately ask vague, evolving questions (e.g., "build a queue using files only," then "no, make it cloud-based") to see how a candidate reasons from an imperfect starting point rather than to get a finished solution.

## Designing a queue backed by files

We worked through what it means to implement a queue — a first-in, first-out structure — using only files, no lists or arrays. We first visualized a queue's possible states: empty, partially full, and full to capacity. Mapping these onto a file, we reasoned that an empty queue is a file of 0 bytes.

With Alexander's suggestion of "just a blank file," we then had to define a length unit for a non-empty queue. We compared counting bytes versus counting lines versus counting serialized-object blocks (e.g., a passenger record with a first name, last name, reservation code, and flight date, wrapped in opening and closing tags similar to XML/JSON). We settled on counting lines for our simplified string-based example, one queue item per line.

We then reasoned through the two core operations: adding an item (create the file if the queue is empty, otherwise append to the end) and removing the first item — a harder case, since files can't delete a single line directly. With Temeeka's help, we arrived at a strategy: read through the file line by line, save the first line separately, write every remaining line to a temporary file, then replace the original file with the temporary one.
