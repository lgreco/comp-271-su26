## String Immutability, Revisited

We opened with a [memory demonstration](./immutability_demo.py): repeatedly appending a string to itself showed the memory address changing every time, proving that Python strings are immutable — an operation that looks like "growing" a string actually creates a brand-new string object each time. After about 30 doublings the combined memory cost climbs into the gigabytes. We connected this directly to our dynamic array's string-building logic, which we said is fine at small scale but should ideally use [`str.join()`](https://docs.python.org/3/library/stdtypes.html#str.join) on a list of items instead of repeated concatenation, since `join` builds only one or two strings rather than one per item.

## Modeling a Train Station as a Linked Object

Using the CTA system as a running analogy, we built up the idea of a [station object](./station.py) with two pieces of state: a `name` (a string) and a `next` reference — a pointer to *another object of the same class*. This is the first time we've defined a class whose field can refer to an instance of itself, the same way each person sitting in a row can "point" to the person on their left. We wrote getter/setter methods (`get_name`, `set_next`, `get_next`) and a predicate accessor, `has_next()`, which returns a boolean instead of the raw reference — a more readable way to ask whether a station is the line's terminus.

## Building the Train Line

We sketched a [`TrainLine`](./trainline.py) class holding just a `head` reference. Adding a station means: if the line is empty, the new station becomes the head; otherwise, walk node by node until we find the station whose `next` is `None`, and attach the new station there. We stopped before implementing this traversal, previewing for Monday a faster approach that tracks the tail station directly instead of walking the whole line each time.
